# 용어 통일

목표는 같은 대상에 한 이름, 한 표기다. 결정은 사용자가 한다. Claude는 후보를 찾아 근거와 함께 묻고, 정해진 것만 반영한다.

도구: `T="${CLAUDE_SKILL_DIR}/scripts/term_tool.py"` (`python3 "$T" -h`로 명령 목록 확인)

## 0. 이미 정한 것부터 찾는다

- 프로젝트의 `.claude/writing-guard.json`(glossary 경로), `.claude/glossary.json`, `**/glossary.json`, `*용어*.md`, 프로젝트 스킬 중 이름에 glossary가 들어간 것을 찾는다.
- 있으면 그것을 정본으로 이어 쓴다. 새 용어집을 따로 만들지 않는다. 이 스킬과 같은 형식(groups → entries → rules)이면 term_tool로 그대로 다룰 수 있다.
- 프로젝트 CLAUDE.md와 문체 문서(`writing-style.md`, `check_style.py` 등)의 용어 규칙도 읽는다. 여기서 정한 것은 다시 묻지 않는다.

## 1. 범위를 정한다

- 인자로 경로를 받지 않았으면 프로젝트 루트의 문서 폴더를 훑는다. 대상 후보가 둘 이상이면 AskUserQuestion으로 묻는다(예: 논문 본문만, 문서 전체, 특정 폴더).
- 현재 원고와 이전 판(`latex_v1`, `backup`, `_old` 등)이 섞여 있으면 현재본이 어느 쪽인지 확인한다. LaTeX는 main 파일이 `\input`하는 폴더가 보통 현재본이다.

## 2. 후보를 찾는다

1. `python3 $T scan <대상> [--include 'glob']`로 기계적 변이를 뽑는다. 철자·대소문자·하이픈·띄어쓰기만 다른 표기, 국문 띄어쓰기 변이, 정의 없이 쓴 약어가 나온다. 목록에는 잡음도 섞이므로 용어가 아닌 것은 버린다.
2. 도구가 찾지 못하는 것은 문서를 직접 읽고 찾는다.
   - 같은 대상을 가리키는 다른 단어(예: 에이전트, agent, 판정기, 모델)
   - 같은 개념을 어떤 곳은 국문, 어떤 곳은 영문으로 쓴 경우
   - 한 단어를 여러 뜻으로 쓴 경우(예: "편향"을 성향, 치우침, 오차에 모두 씀). 뜻마다 이름을 나눠야 한다.
   - 정의와 다른 뜻으로 쓴 약어
   - 대화에서 사용자가 쓰는 표현도 근거로 삼는다.
3. 후보를 개념 단위로 묶는다: 개념, 지금 쓰이는 표기(횟수, 첫 위치), 추천 정본과 이유.
4. 추천 기준은 이 순서를 따른다. 사용자가 이미 정한 것(용어집, CLAUDE.md, 대화) → 그 분야의 표준 용어(학회, 교과서, 공식 문서에서 쓰는 표기) → 프로젝트에서 가장 많이 쓴 표기 → 짧고 오해 없는 표기. 분야 표준을 확신하지 못하면 그렇다고 적는다. 표준을 지어내지 않는다.

## 3. 사용자에게 묻는다 (AskUserQuestion)

- 방침부터 한 번 묻는다. 기술 용어를 국문과 영문 중 무엇으로 쓸지, 약어를 첫 등장 때 풀어 쓸지, 하이픈·대소문자 규칙(예: 정의한 용어는 첫 글자만 대문자). 이미 정해진 방침은 묻지 않는다.
- 그다음 개념마다 질문 하나를 만든다. 한 번 호출에 질문 4개, 선택지 4개까지다. 추천안을 첫 선택지로 두고 "(추천)"을 붙이며, 선택지 설명에 현재 사용 횟수와 추천 이유를 쓴다. 사용자는 "기타"로 직접 입력할 수 있다.
- 질문 순서는 중요도 순이다: 제목·초록·정의에 나오는 핵심 개념 → 자주 나오는 것 → 나머지. 개념이 많으면 핵심 8~12개만 개별로 묻고, 하이픈·대소문자 같은 기계적 차이는 방침 질문 하나로 묶는다.
- 질문 문장은 이 대화를 처음 보는 사람도 이해하게 쓴다. 개념을 한 줄로 설명하고, 어디에 쓰였는지 예를 하나 든다.
- 사용자가 정하지 않은 것은 용어집에 넣지 않는다.

## 4. 용어집에 저장한다

- 위치: 기존 용어집이 있으면 그 파일. 없으면 묻는다. 기본 추천은 `docs/glossary.json`이고, 문서 폴더에 두기 싫으면 `.claude/glossary.json`.
- `python3 $T init <glossary.json>`
- 항목마다:
  `python3 $T add <glossary.json> --group "<분류>" --id <영문-id> --ko "<국문>" --en "<영문>" --meaning "<뜻과 쓰는 법>" --avoid "<쓰지 않는 말, 쉼표로 구분>"`
  - avoid의 말마다 위반 규칙(V)이 자동으로 생긴다. 문맥에 따라 맞을 수도 있는 말은 `--level R`(검토)로 따로 추가한다.
  - 자동 정규식이 정본 표기와 겹친다는 오류가 나면 `python3 $T pattern "<말>" --canonical "<정본>"`으로 확인하고, 필요하면 glossary.json의 rules를 직접 고친다.
- `python3 $T validate <glossary.json>`이 "용어집 OK"를 낼 때까지 고친다.
- `python3 $T render <glossary.json>`으로 사람이 읽는 glossary.md를 만든다. md는 직접 고치지 않는다.
- `python3 $T register <프로젝트 루트> <glossary.json>`으로 전역 writing-guard 훅에 등록한다. 이후 이 프로젝트에서 문서를 고치면 바뀐 줄의 위반을 바로 알리고, 고치지 않으면 응답 종료를 막는다. 매 턴 답변 기준에도 이 용어집 경로가 들어간다.

## 5. 본문을 고친다

- `python3 $T check <glossary.json> <대상>`으로 위반 목록(file:line)을 뽑는다.
- 고치기 전에 규모를 알리고 확인을 받는다: 파일 몇 개, 몇 곳, 예시 세 개. 대량 수정은 되돌리기 번거롭다.
- 바꾸지 않는 것: 인용문, 참고문헌 제목, 코드·명령어·파일명, LaTeX 라벨과 명령, 고유명사(논문 제목, 데이터셋 이름), 남의 글 인용. 바뀐 표기에 조사(을/를, 이/가)가 맞는지 본다.
- sed 같은 일괄 치환보다 Edit로 문맥을 보며 고친다. 양이 많으면 파일 단위로 나누고, 중간에 check로 줄어드는지 확인한다.
- 끝나면 check를 다시 돌려 V 위반 0건을 확인한다. R(검토)은 남아도 되지만 하나씩 봤다고 보고한다.

## 6. 보고한다

정한 용어 수, 고친 곳 수, 그대로 둔 것과 이유, 용어집 경로(json, md), 훅 등록 여부를 쓴다.

## 이후 작업에서

- 이 프로젝트에서 글을 쓰거나 설명할 때 용어집 표기를 쓴다.
- 용어집에 없는 새 개념이 나오면 이름을 지어 쓰지 말고 사용자에게 묻는다. 정해지면 add로 추가하고 render를 다시 돌린다.
- 용어를 바꾸기로 하면 glossary.json을 고치고 validate → render → check 순서로 반영한다.
